# 04. NODEXA CORE: Arquitectura, Stack Tecnológico y Reglas de Ingeniería

**Documento de Referencia Técnica y Contrato de Desarrollo (Línea Base)**

**Objetivo:** Establecer las directrices arquitectónicas, tecnologías autorizadas y reglas imperativas para garantizar que cada línea de código escrita (por humanos o IA) cumpla con los estándares de producción de NODEXA CORE.

---

## 1. Los 7 Pilares Arquitectónicos de NODEXA CORE

Cada módulo o funcionalidad que se incorpore al ecosistema debe respetar estrictamente estos siete principios de diseño:

```
+-------------------------------------------------------------------------+
|                         NODEXA CORE - ARQUITECTURA                      |
+-------------------------------------------------------------------------+
|  1. Modularidad        | Plug & Play mediante Feature Flags por Tenant  |
|  2. Eficiencia         | Paginación estricta, Caché y WebP obligatorio  |
|  3. Seguridad          | OWASP, RLS estricto, Anti-Inyección y Zod      |
|  4. Auditoría          | Logging asíncrono orientados a diffs           |
|  5. Portabilidad       | Patrón Repository + Exportación agnóstica      |
|  6. Trazabilidad       | Sentry (Errores) + PostHog (ROI/Negocio)       |
|  7. UX/UI Intuitiva    | Shadcn UI + Micro-tips y diseño educativo      |
+-------------------------------------------------------------------------+

```

### 1.1 Escalabilidad y Modularidad (Plug & Play)

* **Aislamiento por Feature Flags:** Los módulos adicionales (Catálogo Web, Carga IA, Fiados, Bot WhatsApp) se controlan mediante banderas en base de datos asociadas al `cliente_id` (`tenant_modules`).
* **Desacoplamiento Funcional:** Ningún módulo opcional puede acoplarse rígidamente al núcleo (`Core`). Si un módulo se desactiva, el sistema principal de stock y mostrador debe seguir funcionando al 100%.
* **Code Splitting y Lazy Loading:** Toda vista o componente de un módulo opcional debe importarse de forma dinámica (`import()`) en Next.js para evitar descargar paquetes innecesarios en clientes que no los contrataron.

### 1.2 Eficiencia Máxima y Uso Responsable de Recursos

* **Prohibición de Sobrecarga en BD:** Toda consulta que devuelva listados (productos, clientes, ventas) debe implementar **paginación en el servidor** (mediante cursores o límites de página). Queda terminantemente prohibido ejecutar `SELECT *` sin un `LIMIT` explícito.
* **Guardrails de Multimedia:** Prohibido servir imágenes originales sin procesar. Todas las imágenes cargadas por el usuario deben transformarse y comprimirse de forma automática a formato **WebP (peso objetivo: ~70 KB, máximo 1080px)** antes de almacenarse y mostrarse en el catálogo.
* **Caché Agresiva en Lectura:** Las vistas públicas (Catálogo Web) y paneles de alta rotación deben utilizar caché en el Edge (Next.js Revalidation / TanStack Query) para minimizar los hits transaccionales a PostgreSQL.

### 1.3 Seguridad Transversal (Zero-Trust)

* **Defensa en Profundidad:** Aplicar el estándar de seguridad OWASP Top 10 en todas las capas de la aplicación.
* **Autenticación y Autorización Estricta:** Sesiones con expiración máxima de **1 hora**. Un middleware global en Next.js debe interceptar cada solicitud y validar y decodificar el token de usuario en los endpoints protegidos.
* **Aislamiento Multi-Tenant (RLS + IDOR):** Todo acceso a base de datos debe estar protegido por *Row Level Security* (RLS) en PostgreSQL, garantizando que un `cliente_id` jamás pueda consultar ni modificar filas de otro inquilino.

### 1.4 Auditoría Eficiente y de Bajo Costo

* **Registros Asíncronos:** Toda operación crítica (alta, modificación o baja) debe generar un log de auditoría ejecutado en background (mediante `after()` en Next.js 15 o colas asíncronas) para no penalizar el tiempo de respuesta de la API ni bloquear transacciones.
* **Almacenamiento por Diffs:** Las tablas o sistemas de log no guardan fotos completas de la base de datos, sino únicamente el `diff` (qué campo cambió, valor anterior, valor nuevo, `usuario_id`, `cliente_id` y timestamp).

### 1.5 Portabilidad y Fácil Migración

* **Patrón Repository (Desacoplamiento del ORM/BD):** Los componentes de UI, Server Actions y Rutas no pueden instanciar llamados directos al cliente de base de datos (`@supabase/supabase-js`) ni a APIs de terceros (Cloudinary/OpenAI). Todo se debe abstraer detrás de clases o funciones de repositorio (`src/repositories/`, `src/services/`).
* **Portabilidad de los Datos del Cliente:** El sistema debe contar con mecanismos de exportación en formatos estándar y agnósticos (**CSV / JSON**) para que cualquier usuario pueda extraer su catálogo y transacciones sin fricción.

### 1.6 Trazabilidad Integral (Errores + Negocio)

* **Manejo Exclusivo de Errores Normalizados:** Todo error capturado por el servidor debe mapearse obligatoriamente a los códigos estandarizados del archivo `ERRORS.md`. Prohibido crear códigos o mensajes genéricos al vuelo.
* **Separación entre Monitoreo Técnico y Comercial:**
* **Técnico:** Sentry captura el stacktrace exacto, la ruta y el contexto de ejecución en menos de 500 ms sin exponer datos sensibles.
* **Negocio/UX:** Analytics orientados a eventos (PostHog/Vercel Analytics) trazan visitas, clics en WhatsApp, conversiones del catálogo y uso de módulos del comerciante sin escribir en PostgreSQL.



### 1.7 UX/UI Intuitiva y Educativa

* **Diseño Limpio y Acceso Directo:** Interfaz minimalista que prioriza las funciones críticas de mostrador e inventario a no más de 2 clics de distancia.
* **Educación Contextual (Micro-tips):** Toda funcionalidad nueva o módulo opcional debe ir acompañada de tooltips descriptivos, placeholders con ejemplos reales y guías de uso no invasivas que reduzcan la dependencia del soporte técnico humano.

## 3. Reglas Críticas e Innegociables

### 3.1 Seguridad y Control de Acceso

* **Sanitización Estricta (Input / Output):** Validar absolutamente todo input entrante en Server Actions o API Routes con esquemas **Zod**. Usar **DOMPurify** antes de renderizar cualquier contenido de texto HTML originado por los usuarios para prevenir XSS.
* **Prevención de Inyección SQL/NoSQL:** Prohibida la concatenación de strings o interpolación de variables en consultas SQL. Uso exclusivo de Supabase Query Builder o funciones RPC parametrizadas.
* **Defensa IDOR / BOLA:** Cada endpoint debe verificar en el servidor que el recurso que se desea leer o modificar pertenezca al `cliente_id` del JWT firmado.
* **Políticas RLS en PostgreSQL:** Queda **terminantemente prohibido** crear políticas (`CREATE POLICY`) utilizando `USING (true)` en operaciones `INSERT`, `UPDATE` o `DELETE`. Toda política debe validar explícitamente el inquilino o rol.
* **Perímetro Anti-Abuso:** Implementar **CORS mediante una Allowlist estricta** de dominios permitidos y protección contra fuerza bruta usando `@upstash/ratelimit` en rutas de autenticación, mutación de inventario y consumo de IA.

### 3.2 Escalabilidad y Arquitectura de Dominio

* **Desacoplamiento Estructural:** Aplicar **Clean Architecture** y Diseño Guiado por el Dominio (**DDD**). La capa de interfaz y la lógica de negocio deben comunicarse mediante inyección de dependencias (**DI**) y abstracciones de servicios.
* **Normalización de Base de Datos:** Los esquemas deben estructurarse respetando la **Tercera Forma Normal (3FN)**, salvo excepciones documentadas de desnormalización deliberada para rendimiento de lectura.
* **Idempotencia y Anti-Race Conditions:** Deshabilitar inmediatamente los triggers del frontend al primer clic y utilizar mecanismos de concurrencia optimista en BD para impedir la creación duplicada de ventas o registros al recibir solicitudes simultáneas.

### 3.3 Calidad de Código, Robustez y DX

* **Tipado Estático Fuerte:** Prohibido el uso del tipo `any` en TypeScript. Todas las interfaces, tipos de retorno, DTOs y firmas deben estar completamente tipados.
* **Límites de Tamaño por Archivo:** Queda prohibido escribir archivos que superen las **500 a 600 líneas de código**. Si un archivo excede este tope, debe refactorizarse y dividirse en módulos especializados.
* **Fail-Fast y Validación en la Puerta:** Si un payload no pasa la validación del esquema DTO en la entrada del endpoint, la ejecución se interrumpe de inmediato devolviendo un error HTTP con formato estandarizado.
* **Idioma de Desarrollo:** Todo nombre de función, variable, parámetro, clase, tipo y comentario debe redactarse en **Español Latinoamericano** (`crearUsuario`, `obtenerHistorialVentas`, `clienteId`). Quedan reservados al inglés únicamente las palabras reservadas de librerías o de la base de datos (ej. `select`, `id`, `created_at`).

### 3.4 Pirámide de Testing y Calidad

* **Enfoque TDD (Test-Driven Development):** El desarrollo de funciones de negocio core y cálculos de caja/stock debe iniciarse con la redacción del caso de prueba.
* **Proporción Estricta de Pruebas:**
* **70% Pruebas Unitarias (Vitest):** Funciones de cálculo, transformadores de datos, utilidades y reglas matemáticas.
* **20% Pruebas de Integración:** Verificación de Repositorios, Server Actions, políticas RLS en Supabase y rechazo de inputs maliciosos.
* **10% Pruebas End-to-End / E2E (Playwright):** Flujos críticos del usuario (Onboarding de comercio, alta de producto y cobro en mostrador).



### 3.5 Trazabilidad y Manejo de Excepciones

* **Integración del Catálogo de Errores (`ERRORS.md`):** Todo error del sistema, de permisos o de base de datos arrojado al frontend debe corresponder exactamente a los códigos definidos por arquitectura (ej. `NX-SYS-001`, `NX-PER-001`).
* **Comunicación Empática en Cliente:** El mensaje visual renderizado en cliente nunca debe exponer excepciones técnicas, trazas de SQL ni nombres de columnas; debe ofrecer un lenguaje claro, educado y orientado a la solución.
* **Prohibición de Logs Sensibles:** Queda prohibido el uso de `console.log()` que exponga contraseñas, tokens de acceso, claves API o datos privados en terminales o herramientas de monitoreo.
* **Borrado Lógico (Soft Delete):** Queda prohibida la eliminación física (`DELETE`) sobre entidades principales de negocio (`productos`, `ventas`, `clientes`). Se debe utilizar el patrón de borrado lógico mediante la columna `eliminado_en` (`TIMESTAMP NULL`).

### 3.6 Infraestructura, Gestión de Claves y DevOps

* **Prohibición de Hardcoding y Fugas en NEXT_PUBLIC:** Terminantemente prohibido escribir claves de acceso, contraseñas o API Keys directamente en el código fuente. Queda prohibido exponer credenciales sensibles utilizando variables que comiencen con el prefijo `NEXT_PUBLIC_`.
* **Aislamiento de la Service Role Key:** La clave `service_role` de Supabase únicamente puede importarse y utilizarse en módulos que se ejecuten en entornos de servidor dedicados a tareas administrativas o cron jobs, jamás accesible desde el navegador del cliente.
* **Infraestructura Automatizada:** Todo despliegue sobre entornos de pre-producción y producción se ejecuta de manera automatizada a través de pipelines **CI/CD**, requiriendo que pasen todas las pruebas automáticas, linters y validaciones de tipos antes de cada publicación.
